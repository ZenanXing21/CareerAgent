# 人才池长期记忆设计

## 目标

同一工作区的多个简历 session 共享一份人才档案。用户在聊天中明确陈述自己的技能、经历或成果后自动入池；用户明确要求从人才池删除时删除。JD 仅用于挑选与排序，不当作候选人事实。

## 数据边界

- `session` 继续保存单次任务的聊天、JD、简历版本和编辑历史。
- `talent_pool` 由工作区拥有，按现有 `workspace_owner` 隔离，存储在工作区快照中。
- 每条事实保存类别、规范化内容、原文、来源 session、来源类型和时间。相同事实去重，保留多个来源。
- 从简历或用户第一人称陈述抽取事实；分析 JD 时不得把要求写入人才池。
- 删除指令必须明确指向人才池及具体事实。删除后记录墓碑，防止后续重放旧 session 时重新入池。用户再次明确添加可解除墓碑。

## 生成流程

1. 在开始 JD 定制时检索人才池，按岗位词汇和语义相关性排序事实。
2. 只把相关且有来源的事实作为生成素材；保留原始事实，不为了匹配 JD 发明经历。
3. 当前 session 的用户指令优先于人才池。生成结果只写回当前 session，不修改人才池原文。
4. 在界面展示本次采用的事实及来源，让用户能纠正和删除。

## 验收

- 在 session A 提到新技能，session B 的人才池能读取。
- 不相关 JD 不自动塞入该技能；相关 JD 能选用。
- JD 中独有的技能不会入池。
- 明确删除后所有 session 不再检索到，重启服务后仍有效。
- 其他工作区不可读取该人才池。

## 跨设备

当前系统没有账号，工作区密钥由浏览器保存。跨设备同步需要先建立登录与身份绑定；在这之前“同一用户”只能可靠地界定为同一工作区。
